#+TITLE: FAVOR-Style Bitset Filtering for CAGRA
#+AUTHOR: Nam Anh Dang
#+OPTIONS: toc:2

* Purpose and scope

This document records the plan used to implement FAVOR-style filtering in
CAGRA, the changes that were actually made, and the procedure used to reproduce
the SIFT-1M benchmarks and Pareto-frontier plots.

The implemented scope is intentionally narrower than the full design in
=plan.org=:

- only bitset filters are supported;
- selectivity is exact and shared by the whole query batch;
- only CAGRA =SINGLE_CTA= search is supported;
- there is no UDF selectivity estimator or per-query runtime-state structure;
- there is no FAVOR-specific termination condition, bounded retry, or
  =MULTI_CTA= implementation;
- default CAGRA filtering remains the default.

The external reference implementation used while interpreting the algorithm is
the FAVOR source tree at =/users/namanh/FAVOR=. The GPU implementation here is
not copied from that CPU/HNSW code: it adapts the scoring idea to CAGRA's
existing shared-memory search loop.

* Plan

The implementation followed this order:

1. Build one attribute-independent SIFT-1M CAGRA graph with graph degree 32 and
   intermediate graph degree 64.
2. Compute the graph/dataset-specific FAVOR =delta_d= value, save it in a
   validated sidecar, and verify that the sidecar can be loaded.
3. Add an opt-in FAVOR search mode while leaving default CAGRA behavior as the
   API default.
4. For a bitset, count passing graph rows once on the host-side search path and
   pass the resulting shared rejection rate through the existing
   =filtering_rate= field.
5. Select a separate FAVOR =SINGLE_CTA= JIT kernel.
6. Compute one penalty value per query CTA and reuse it for all candidates
   handled by that CTA.
7. Fuse the bitset check and penalty into initial-node and child-node distance
   calculation. Do not add a separate post-distance synchronization and
   read/modify/write phase.
8. Preserve rejected nodes for graph traversal by assigning their penalized
   distance. Apply the bitset when producing final results.
9. Add benchmark support for persistent bitsets, matched default/FAVOR
   configurations, and delta-d sidecar loading.
10. Compare recall/throughput for 10,000 queries and recall/batch-latency for
    10 queries at 1%, 10%, 50%, and 90% selectivity.

* Search behavior

** Selectivity and penalty

For this bitset-only implementation, let:

- =p= be exact selectivity, the fraction of graph rows whose bit is set;
- =r = 1 - p= be the rejection/filtering rate;
- =ef= be CAGRA's internal top-k size;
- =delta_d= be the graph/dataset statistic loaded from the sidecar.

The kernel receives =r= through =search_params::filtering_rate= and computes:

#+begin_src text
p = 1 - filtering_rate
D = filtering_rate * (ef - p) * delta_d / (2 * p * ef)
#+end_src

Thread 0 computes =D= once at CTA initialization and writes it to shared
memory. The synchronization already used by initialization makes it visible to
the distance-computation teams, so this does not add a standalone
synchronization phase.

An exact selectivity of zero is detected before kernel launch. Search is
skipped and the output is filled with invalid indices and maximum distances.

** Fused candidate scoring

FAVOR-specific variants of the initial-random-node and child-node distance
functions perform these operations together:

#+begin_src text
compute vector distance
map the internal graph ID to the source ID when necessary
have one lane in the distance team check the bitset
share that result within the team
add D when the row does not pass
write the candidate and final score once
#+end_src

Rejected nodes are therefore retained as penalized traversal candidates.
Default CAGRA instead follows its existing invalidation path. The compile-time
=FAVOR= specialization keeps the two inner search paths separate.

** Final filtering and the MSB sentinel correction

CAGRA uses the most-significant index bit to mark nodes whose distance has
already been calculated/expanded. Final compaction clears this bit before
interpreting an index.

The invalid sentinel is an all-one index. Clearing its MSB changes its numeric
representation. The old comparison cleared the candidate's MSB but compared it
with the unmodified sentinel, causing an invalid entry to be counted as valid:

#+begin_src cpp
(candidate & ~msb_mask) == invalid_index
#+end_src

The corrected comparison normalizes both sides:

#+begin_src cpp
(candidate & ~msb_mask) == (invalid_index & ~msb_mask)
#+end_src

Without this correction, rejected rows could occupy final output positions and
FAVOR recall plateaued, especially at higher selectivity. The compaction code
is shared, so this is also a correctness fix for default filtered CAGRA when an
invalid sentinel reaches that stage.

* Implemented changes

** Public API and delta-d support

- =cpp/include/cuvs/neighbors/cagra.hpp=
  - added =filtering_mode { DEFAULT, FAVOR }=;
  - appended =filter_mode= and =favor_delta_d= to =cagra::search_params=;
  - kept =DEFAULT= as the default value;
  - exposes =favor_delta_d_params= and compute/save/load APIs.
- =cpp/src/neighbors/cagra_favor_delta_d.cu= and routing in
  =cpp/src/neighbors/cagra.cuh=
  - compute =delta_d= from a prebuilt graph using bounded BFS neighborhoods;
  - store metadata and the scalar in a sidecar;
  - validate graph, dataset, metric, dimensions, degree, parameters, and file
    integrity when loading.
- =examples/cpp/src/cagra_favor_compare.cu=
  - computes CAGRA =delta_d=, compares it with a matched FAVOR reference run,
    writes the sidecar, reloads it, and verifies exact scalar preservation.

FAVOR search rejects missing/non-finite delta-d values, a non-bitset filter,
and unsupported search algorithms.

** Search routing and JIT kernel

- =cpp/src/neighbors/cagra.cuh=
  - counts exact bitset matches;
  - places the shared rejection rate in =filtering_rate=;
  - handles an empty bitset without launching search;
  - rejects FAVOR for no-filter and UDF-filter calls.
- =cpp/src/neighbors/detail/cagra/search_plan.cuh= and
  =search_single_cta.cuh=
  - select FAVOR only for =SINGLE_CTA=;
  - reserve one shared distance scalar for the CTA penalty;
  - preserve the existing default plan.
- =cpp/src/neighbors/detail/cagra/jit_lto_kernels/device_common_jit.cuh=
  - adds fused FAVOR variants for initial random candidates and graph
    children.
- =cpp/src/neighbors/detail/cagra/jit_lto_kernels/search_single_cta_jit.cuh=
  - specializes the shared search core at compile time;
  - computes the CTA penalty;
  - routes scoring to the fused FAVOR functions;
  - leaves default parent invalidation under =!FAVOR=;
  - filters and compacts the final result;
  - contains the normalized-MSB sentinel fix.
- =search_single_cta_favor_kernel.cu.in=, =kernel_def.hpp=,
  =cagra_jit_launcher_factory.hpp=, =search_single_cta_planner.hpp=,
  =search_single_cta_kernel_launcher_jit.cuh=, and
  =cagra_fragments.hpp=
  - define, build, link, select, and launch the FAVOR JIT/LTO kernel variants.
- =cpp/CMakeLists.txt=
  - includes FAVOR kernel generation in the build.

** Tests

=cpp/tests/neighbors/ann_cagra/test_favor_search.cu= covers:

- implicit default mode equals explicit =filtering_mode::DEFAULT=;
- an accept-all FAVOR filter matches default search;
- FAVOR returns only passing rows;
- final top-k compacts rejected rows even when =favor_delta_d= is zero;
- an empty filter returns sentinels without searching;
- missing delta-d and non-bitset FAVOR calls fail.

The existing delta-d tests cover GPU/CPU calculation agreement, persistence,
metadata mismatch, malformed files, and invalid inputs.

- dataset configuration accepts =filter_bitset_file= and loads the same

- CAGRA search configuration accepts =filter_mode=, =favor_delta_d=, and

** Compute and save delta-d second

Delta-d must be computed after graph construction because its sidecar is bound
to the graph and attached dataset. The essential API sequence is:

#+begin_src cpp

index.update_dataset(res, dataset_view);
auto params = cagra::favor_delta_d_params{10, 64, 2};
auto delta_d = cagra::compute_favor_delta_d(res, params, index);
cagra::save_favor_delta_d(res, graph_path + ".delta_d", params, index, delta_d);
auto checked = cagra::load_favor_delta_d(
  res, graph_path + ".delta_d", params, index);
#+end_src

* Current benchmark interpretation

With the graph and sweep above:

- at 1% selectivity, FAVOR has a large advantage because penalized rejected
  nodes remain available as bridges through an otherwise highly fragmented
  filtered graph;
- at 10% and above, default CAGRA has enough passing nodes for effective
  traversal, while FAVOR still pays for per-candidate bitset checks and
  penalized-candidate competition;
- at 50% and 90%, both methods reach approximately 0.999 recall and the small
  performance difference is primarily FAVOR overhead;
- the observed crossover on this dataset lies between 1% and 10%, but it is not
  assumed to generalize to other graphs, dimensions, or datasets.

Maximum measured FAVOR recall in the final one-repetition sweep was:

| Selectivity | 10,000-query throughput run | 10-query latency run |
|-------------+-----------------------------+----------------------|
|          1% |                     0.95473 |              0.95567 |
|         10% |                     0.98981 |              0.98913 |
|         50% |                     0.99940 |              0.99952 |
|         90% |                     0.99939 |              0.99937 |

** BIGANN 10% penalty diagnosis

A focused diagnostic isolates three possible explanations for the low 10%
FAVOR recall:

1. a miscalibrated penalty;
2. insufficient search iterations;
3. insufficient search width.

Generate and run all focused configurations with one repetition using:

#+begin_src sh

#+end_src

The command writes:

| Dataset    | Delta-d multiplier | Effective D | Recall@10 |
|------------+--------------------+-------------+-----------|
| BIGANN-1M  |            0.00010 |       0.619 |   0.98938 |
| BIGANN-1M  |            0.00015 |       0.929 |   0.94979 |
| BIGANN-1M  |            0.00020 |       1.239 |   0.87890 |
| BIGANN-1M  |            0.00030 |       1.858 |   0.82734 |
| BIGANN-1M  |            0.00050 |       3.097 |   0.82510 |
| BIGANN-10M |            0.00010 |       0.485 |   0.96276 |
| BIGANN-10M |            0.00015 |       0.728 |   0.88699 |
| BIGANN-10M |            0.00020 |       0.970 |   0.78114 |
| BIGANN-10M |            0.00030 |       1.455 |   0.70689 |
| BIGANN-10M |            0.00050 |       2.425 |   0.70373 |

The normal multiplier is 1.0, corresponding to =D=6194 for BIGANN-1M and
=D=4850 for BIGANN-10M. Recall has already saturated at its low plateau by
=D=3.1= and =D=2.4= respectively. This rules out a penalty that is too small.
It shows that the delta-d formula is severely over-calibrated for these
=uint8= BIGANN graphs at 10% selectivity.

Increasing independent traversal budget does not recover recall:

CAGRA requested about 10.5 GB of iteration state, beyond the 6.3 GB RMM limit
available to this process. The valid 1024-iteration point already doubles the
default traversal budget and does not materially change the conclusion.

The default path improves normally as width grows, while FAVOR remains pinned
to the penalty-induced plateau. FAVOR with =D=0= exceeds 0.98 recall on both
datasets, proving that the graph, bitset, final compaction, and basic FAVOR
=uint8= dispatch can reach high recall. The local =uint8= regression tests also
pass. The failure is therefore caused by penalized traversal ordering for this
workload, not by a generally poor graph or too little search.

For this deterministic BIGANN workload, a practical calibration must keep
=D= below roughly 0.7 if 90% recall is required at 10% selectivity. Choosing
such a clamp or changing the delta-d estimator is an algorithm-policy change
and is not silently applied by the benchmark diagnostic.

* CAGRA-specific static penalty experiment

The HNSW-derived penalty can evict rejected traversal bridges from CAGRA's
shared traversal/result candidate buffer. The static experiment tests whether
the penalty should be reduced once =internal_topk= is likely to contain the
requested number of passing results.

For =B=internal_topk=, passing selectivity =p=, and requested result count =k=,
the host models the number of passing candidate slots as:

#+begin_src text
X ~ Binomial(B, p)
P_short = Pr[X < k]
#+end_src

=P_short= is calculated once per =(B,p,k)= benchmark configuration. It is not
calculated per query or in the CUDA kernel, and it does not allocate another
candidate buffer. The experiment scales the delta-d scalar already accepted by
the kernel:

#+begin_src text
D_current = ((1-p) * (B-p) * delta_d) / (2*p*B)
D_test = multiplier * D_current

current: multiplier = 1
zero:    multiplier = 0
hard05:  multiplier = 1 if P_short > 0.05 else 0
hard10:  multiplier = 1 if P_short > 0.10 else 0
smooth2: multiplier = P_short^2
smooth4: multiplier = P_short^4
#+end_src

The driver writes a manifest containing =P_short=, the multiplier, the original
and scaled delta-d values, and the expected applied penalty for every search
parameter. Generated cuvs-bench JSON contains only the existing direct
=favor_delta_d= scalar.

Run the formula checks and screening stage with:

#+begin_src sh
python benchmarks/favor/static_penalty_experiment.py check
python -m unittest discover -s benchmarks/favor \
  -p 'test_static_penalty_experiment.py' -v

python benchmarks/favor/static_penalty_experiment.py generate \
  --result-dir benchmarks/favor/results_static_penalty_screen \
  --datasets sift bigann1m msturing1m \
  --selectivities 1 2 3 4 5 6 7 8 10 50 90 \
  --itopk-values 512 --search-widths 1 2 4 \
  --batch-sizes 10000 \
  --formulas current zero hard05 hard10 smooth2 smooth4

benchmarks/favor/run_static_penalty.sh \
  benchmarks/favor/results_static_penalty_screen
#+end_src

The runner reuses complete results and then creates =summary.csv=,
=formula_comparison.csv=, and one clearly labeled Pareto plot for every
available dataset/selectivity/workload combination. A custom experiment can use
any subset of dataset keys, selectivities, =internal_topk= values, widths, batch
sizes, or formulas accepted by the generator.

** Static penalty results

The screening stage measured 693 points on SIFT-1M, BIGANN-1M, and MSTuring-1M.
The best hard gate was =epsilon=0.10= and the best smooth gate by worst-case
recall gap was =r=4=. Both preserved the full penalty at very low selectivity
and removed BIGANN's severe full-penalty collapse after the 2--3% transition.

The held-out validation measured 2,475 points on GIST-1M, BIGANN-10M, and
MSTuring-10M over the full =internal_topk={32,64,128,256,512}= and
=search_width={1,2,4}= grid. Neither finalist passed the predeclared recall
constraint:

| Dataset    | Selectivity | Best baseline max recall | Hard 0.10 | Smooth r=4 |
|------------+-------------+--------------------------+-----------+------------|
| BIGANN-10M |          2% |                  0.93135 |   0.91499 |    0.91495 |
| BIGANN-10M |          8% |                  0.99190 |   0.98012 |    0.98012 |
| BIGANN-10M |         10% |                  0.99452 |   0.98252 |    0.98251 |

Both formulas also remained below 0.90 recall on MSTuring-10M at 8%, where
default CAGRA reached 0.90712. The exact failed cells and QPS regrets are in
=results_static_penalty_validation/selection.json=.

There is therefore no static-formula winner, and the final low-batch latency
sweep was intentionally not run. This follows the experiment's stopping rule:
do not tune constants on the held-out datasets when no formula using only
=p=, =B=, =k=, and global =delta_d= satisfies the constraints.

The result rules out =P_short= as a complete CAGRA penalty controller. It is
useful for detecting candidate scarcity, but it cannot model query-local
distance gaps, graph-correlated candidate discovery, or the rejected bridge
nodes required for traversal. The next design should use query-local candidate
statistics or separate traversal priority from passing-result retention.

* Known issue

On the current environment, =CUVS_CAGRA_ANN_BENCH= sometimes exits with status
139 during CUDA/process teardown after it has closed a complete JSON result.
The runner does not ignore arbitrary crashes: it accepts a nonzero exit only
after parsing the JSON and verifying exactly 30 unique iteration rows with no
benchmark error flags. Incomplete results still fail the run.

* Backwards compatibility

- =filter_mode= defaults to =DEFAULT=.
- New search fields were appended and old benchmark configuration fields remain
  valid.
- Default scoring and filter invalidation remain in the non-FAVOR compile-time
  branch.
- An explicit-default regression test matches the result of the legacy
  implicit/default selection.
- The normalized-MSB comparison is shared and can correct invalid-sentinel
  handling in default filtered search; therefore results affected by the old
  compaction bug may improve rather than remain bit-for-bit identical.

* Deferred work

The following items from =plan.org= were not implemented:

- UDF filters and sampled/per-query selectivity;
- a FAVOR runtime-state structure;
- filter-aware termination or bounded retries;
- =MULTI_CTA= FAVOR kernels;
- brute-force fallback below an adaptive selectivity threshold;
- automatic selection between default and FAVOR near the measured crossover;
- evaluation on additional predicates beyond the deterministic bitsets used
  for SIFT, GIST, BIGANN, and MSTuring.
