#+title: NaviX GPU optimization and CPU baseline report
#+options: toc:3 num:t

* Status

This report is the canonical implementation and evaluation artifact.  The implementation is
complete.  GPU correctness, the complete primary and five-policy B0 sweeps, two
optimization-ablation gates, all native CPU graphs, the =8/16/32=-thread scaling gate,
deterministic-seed ablations, and every conditional deep sweep are complete.  The original plan is
retained so deviations and rejected optimizations remain auditable.

* Research questions

1. Can strict bitmap-seeded NaviX be made materially faster on GPU without changing its traversal
   semantics, result set, graph budget, or public cuVS API?
2. Which costs dominate the current kernel: generic bitmap dispatch, eager bridge setup,
   two-hop synchronization, distance work, registers, or shared-memory occupancy?
3. How does optimized GPU NaviX compare with default CAGRA, default CAGRA plus its passing-result
   accumulator, CPU FAISS-NaviX, ACORN-1, and ACORN-gamma?
4. How much of ACORN's recall and underfill gap is caused by its lack of the deterministic passing
   seeds used by both NaviX implementations, rather than its graph or traversal policy?

* Original implementation plan

** Scope and semantic contract

- Optimize strict bitmap-seeded, non-persistent, degree-32 NaviX for CAGRA =SINGLE_CTA=.
- Keep strict bitmap seeding: select the first =k= passing internal graph IDs in ascending order;
  never add random or rejected seeds.
- Preserve the degree-32 adaptive-local policy.  If =P= of the 32 first-hop neighbors pass, use
  one hop for =P >= 13=, blind two-hop for =P <= 4=, and directed two-hop otherwise.
- Persist only passing nodes in CAGRA's fused =itopk=.  Rejected nodes may be transient bridges but
  never persistent frontier entries.
- Preserve raw squared-L2 ordering, the fused =itopk + W*D= candidate tail, parent selection,
  merging, expansion tags, deterministic bridge order, and B0/max-iteration accounting.
- Retain the existing =W*D= bridge-ID buffer.  Grandchildren remain warp-local register values;
  never allocate a =D*D= shared-memory buffer.
- Include the bitmap seed prepass in end-to-end timing, but do not charge it graph iterations.
- Preserve query offsets, source-index remapping, invalid sentinels, and underfilled-row behavior.
- Add no public cuVS search field, overload, filter type, fallback mode, or accumulator behavior.

** Isolated reference and optimized kernels

- Work on branch =navix-single-cta-kernel-opt= in a clean worktree, leaving the dirty
  =favor-filtered-search= checkout untouched.
- Add benchmark-private selection between =reference= and =optimized= NaviX kernels.
- Compile separate JIT specializations so reference code does not inflate the optimized kernel's
  register count.  Keep the existing serial/tiled scheduler control orthogonal.
- Freeze current strict-bitmap outputs as the golden reference.

** CTA-local bitmap lookup

- Hoist the bitmap pointer, dimensions, native packing flag, effective query row, 64-bit row start,
  aligned row pointer, and source-map status once per CTA.
- For a native, word-aligned row with identity IDs, test
  =row_words[source_id >> 5] & (1u << (source_id & 31))= through the read-only cache.
- For unaligned rows, non-native =original_nbits=, or source-index remapping, use an exact fallback
  matching RAFT's =bitmap_view.test(row, source)=.
- Use the direct lookup in both first- and second-hop traversal.  Leave UDF and other filter types
  on the generic linked path.
- Test warp grouping for repeated bitmap-word addresses with =__match_any_sync=, retaining it only
  if its measured benefit exceeds its instruction/register cost.

** Lazy bridge lifecycle

1. Clear only the mandatory =W*D= output IDs and distances.
2. Load/filter first-hop rows, ballot =P=, resolve policies, and publish a two-hop-parent mask.
3. For one-hop parents, insert and compact passing children without touching bridge state.
4. For blind/directed parents, initialize only their bridge count and stably compact rejected
   first-hop nodes.
5. If every parent is one-hop, skip the bridge phase and its CTA barriers entirely.

Only the initialized =bridge_count= prefix may be read, so stale unused bridge entries are safe.

** Distance-work reduction

- Compute passing-node distance only after successful visited admission.
- Never compute rejected one-hop or rejected second-hop distance.
- Blind mode computes no rejected-node distance.
- Directed mode necessarily computes one raw distance for each unique, previously unvisited
  rejected first-hop bridge so it can order bridge expansion.
- Use a read-only visited check before directed bridge distance and never recompute an available
  value.
- Test separating passing compaction from rejected directed sorting.  Keep it only when final IDs
  and distances remain exactly identical.

** Warp-cooperative two-hop producer/consumer scheduler

For each two-hop parent and bridge tile:

1. Assign consecutive bridge rows to resident warps.
2. Each producer warp performs one coalesced 32-ID graph-row load, maps IDs if required, applies
   direct bitmap tests, ballots passing lanes, and retains IDs/mask in registers.
3. Publish one 32-bit pass mask per producer warp.
4. Consume nonempty producer rows in original bridge order.  The owner warp applies visited
   insertion, stable lane compaction, and appends up to the =D= cap.

- Reserve masks for at most eight warps, matching the 256-thread tuning ceiling.
- Skip commit turns for empty pass masks.
- Keep CTA synchronization between nonempty ordered commits so later rows observe earlier hash
  insertions and the current output count.
- Remove only demonstrably redundant pre-commit synchronization.
- Use the actual active-warp count in a partial tile and uniformly stop loading new tiles at the
  candidate cap.
- Do not parallelize semantic commits across bridge rows or introduce degree-squared staging.

** Launch and occupancy tuning

- Compile/test 64, 128, and 256 threads per CTA.
- Record registers/thread, static/dynamic shared memory, active blocks/threads/warps per SM, the
  limiting resource, kernel time, and end-to-end time.
- Profile representative configurations for active warps, barrier stalls, long-scoreboard stalls,
  graph/bitmap traffic, and branch efficiency.
- Use three repetitions and median QPS for small optimization gates; use one repetition for the
  complete sweep.
- Retain an optimization only if outputs are exact, correctness counters remain zero, hard-workload
  median QPS improves by at least 2 percent (or the change enables a combined improvement), no
  representative EM/R configuration regresses by more than 2 percent, and resource growth does not
  create a harmful residency tier.

** CPU baselines

*** FAISS-NaviX

- Build standard HNSW graphs.  The completed ArXiv graphs and the exploratory YFCC graph use
  =M=32= and =efConstruction=200=.  Every subsequent YFCC build used for the final comparison must
  instead use the [[https://arxiv.org/html/2602.10258][JAG Appendix D.5]] NaviX setting: =M=64= and
  =efConstruction=200=.
- Set =index.hnsw.efSearch= directly for every sweep point.
- Replace the fixed 4,096-ID two-hop scratch with degree-derived per-worker storage of =D + D^2=
  IDs.  The exploratory =M=32= graph has level-zero degree =D=64= and needs 4,160 entries; the
  JAG-aligned =M=64= YFCC graph has =D=128= and needs 16,512.  This allocation is derived from the
  loaded graph, so changing =M= cannot silently overflow the NaviX workspace.
- Preserve native mask semantics, source-order IDs, and squared L2.

*** ACORN

- Run paper-faithful ACORN-1 with =gamma=1= and =M_beta=M=.  Its construction corresponds to
  original HNSW construction *without pruning*, not to the separately built heuristic-pruned
  FAISS HNSW graph.  Its search performs full one-hop plus two-hop neighbor expansion, predicate
  filtering, and truncation back to =M=.  Do not use the repository demo's =M_beta=2M= setting
  under the ACORN-1 label.
- Build workload-specific ACORN-gamma graphs:
  - ArXiv EM: =M=16=, =M_beta=24=, =gamma=10=, =efConstruction=160=.
  - ArXiv R: =M=32=, =M_beta=24=, =gamma=12=, =efConstruction=384=.
  - ArXiv EMIS: =M=16=, =M_beta=24=, =gamma=15=, =efConstruction=240=.
  - YFCC: every subsequent graph used for the final comparison must use the
    [[https://arxiv.org/html/2602.10258][JAG Appendix D.5]] ACORN setting =M=64=, =gamma=30=, and
    =M_beta=64=.  The paper does not list a separate
    ACORN =efConstruction= value in that parameter table, so the actual constructor value must be
    recorded as an implementation setting rather than attributed to JAG.  The obsolete
    =M=32=, =M_beta=32=, =gamma=100= exploratory build was terminated before serialization and
    produces no result or graph used by this report.
- Sweep =efSearch={10,15,20,25,30,50,100,250,500,750}= and set
  =index.acorn.efSearch= directly.
- Test upstream ACORN first and apply a labeled correctness patch only if a concrete test fails.
- Configure CMake 4.4 with =CMAKE_POLICY_VERSION_MINIMUM=3.5= and system zlib headers.

Convert YFCC uint8 coordinates exactly to float32; use native ArXiv float32.  Use CPU masks exactly
matching the GPU predicate.  Test YFCC mask chunks of 128/256/512 queries and select the smallest
within 2 percent of the best throughput; ArXiv may process 10,000 queries in one call.

** Validation and throughput protocol

- Exhaustively test aligned/unaligned rows, source-ID permutations, query offsets,
  native/non-native packing, empty rows, fewer-than-k rows, all-pass rows, and sparse random rows.
- Compare direct lookup against RAFT for every fixture bit.
- Compare reference/optimized seeds, final IDs, and distances for forced one-hop, directed, blind,
  adaptive-Kuzu, and adaptive-paper modes at 64/128/256 threads.
- Require zero filter violations and correct invalid sentinels.
- Correctness uses 1,000 queries; throughput covers 10,000 queries with =k=10=, degree 32,
  =L={64,128,256,512}=, =W={1,2}=, and B0 (=max_iterations=0=).
- ArXiv uses one 10,000-query host call.  YFCC uses four 2,048-query calls and one 1,808-query call.
  With =max_queries=512= both workloads execute 20 internal CAGRA chunks.  YFCC aggregate QPS is
  =10000 / sum(the five end-to-end call times)=.
- Do not add deeper settings after approximately 0.95 recall is reached.

GPU plots compare default CAGRA, default plus accumulator, reference strict-bitmap NaviX, and
optimized strict-bitmap NaviX.  CPU plots compare FAISS-NaviX, ACORN-1, ACORN-gamma, and explicitly
labeled ACORN variants given the same ten deterministic passing seeds as NaviX.  CPU and GPU receive
separate primary panels; an absolute-QPS overlay is appendix-only.  QPS axes begin at zero and
important parameter values are annotated.

* Implementation

** GPU experiment isolation

Work is isolated in =/home/ubuntu/cuvs-filter-navix-opt= on branch
=navix-single-cta-kernel-opt=.  The original dirty =/home/ubuntu/cuvs-filter= checkout was not
modified.  Commit =7897dc27= records this plan before implementation.

The GPU experiment adds only benchmark-private machinery:

- =navix_kernel_variant={reference,optimized}= is accepted by cuVS-bench, not by the public CAGRA
  search API.
- Reference and experimental NaviX use distinct JIT tags and kernel fragments, preventing the
  experiment from silently changing the reference binary.
- =CUVS_NAVIX_LOG_RESOURCES=1= reports CUDA function attributes and occupancy.
- A reduced generator separates 1,000-query correctness, a small 10,000-query acceptance gate,
  the complete B0 frontier, and conditional deeper runs.

The first experimental specialization hoisted bitmap-row metadata, used an aligned direct packed
word lookup, skipped unused bridge initialization, and initially tested a per-parent scheduler
counter.  The counter was removed after it introduced hot-path serialization.  The direct lookup
was subsequently removed after its CTA setup barrier and row-descriptor traffic produced a stable
regression.  The final isolated ablation differs from reference only by omitting eager writes to
bridge slots and per-parent counters that are overwritten before their bounded prefixes are read.
It is performance-neutral and is therefore not proposed for merge.

** CPU baselines

The native FAISS-NaviX runner is on branch =faiss-navix-native-benchmark=.  It:

- consumes the same packed query-by-database bitmap as GPU;
- sets =index.hnsw.efSearch= directly for each point;
- replaces the unsafe fixed 4,096-ID two-hop workspace with =D + D^2= IDs (4,160 at level-zero
  degree 64);
- uses native float ArXiv vectors and exact float conversion of YFCC bytes; and
- writes graph-build time/size sidecars independently of search timing.

The ACORN runner is on branch =acorn-gamma-benchmark=.  It builds independent ACORN-1 and
workload-specific ACORN-gamma graphs, sets =index.acorn.efSearch= directly, fixes invalid neighbor
reads, prevents a rejected entry point from leaking into results, and makes save/load own safe
zero-valued construction metadata.  A fixture proves graph topology is unchanged when construction
metadata values change.  The query bitmap remains the only search predicate.

A follow-up branch, =acorn-navix-seeds=, adds a benchmark-only =filtered_seed_count= search
parameter whose default of zero is output-identical to the reference path.  At ten seeds it matches the
corrected FAISS-NaviX initialization order: preserve the HNSW upper-layer nearest node as a traversal
candidate; admit it to results only if it passes; scan source IDs in ascending order until the first
ten passing IDs have been observed; skip an already visited overlap; compute exact distances; add
each new seed to the independent result heap before the bounded traversal heap can evict it; and
mark every admitted seed visited.  The subsequent ACORN-1 or ACORN-gamma traversal is unchanged.
Thus these curves isolate seeding on the *same serialized ACORN graph* and are labeled
=ACORN-* + NaviX seeds=, never as reference ACORN.

The runner synchronizes both =index.acorn.efSearch= and the per-call
=SearchParametersACORN::efSearch=.  The fork uses the former to size its bounded candidate heap and
the latter for termination; setting only one silently changes the intended sweep.  Seed distance
work occurs inside the timed native search call.  Predicate cardinalities used only for correctness
classification are cached once in parallel after search, outside reported QPS, rather than
serially rescanning the 10M-bit row for every =efSearch= value.

The initial CPU measurements use eight OpenMP threads as the lower endpoint of the local scaling
gate.  The arxiv-for-fanns paper executed queries with one thread on a machine that had eight
hardware threads, so our eight-thread QPS is *not* labeled a paper reproduction.  For the final
resource comparison, one complete L4 is compared against the best measured local CPU setting,
not against an arbitrary CUDA/CPU thread equivalence.
The runners therefore expose independent build/search thread counts.  Final CPU search uses an
=8/16/32=-thread scaling gate and selects the best setting; the new YFCC graphs use 24 OpenMP
construction threads, which is outside timed search.  Both counts are recorded separately.  The
eight-thread results remain a local scaling reference rather than the primary speedup denominator.

* Correctness

The complete bitmap GTest suite passes: *42/42 tests*.  The optimized/reference test covers an
unaligned 769-column bitmap, source-ID remapping, one-hop, directed two-hop, and blind two-hop
policies.  For every case, final IDs and distances are exact, not merely equal in aggregate recall.

The 1,000-query real-data sweep covers YFCC, ArXiv-EM, ArXiv-EMIS, and ArXiv-R under all five NaviX
policies.  Reference and the corrected experimental kernels have zero filter violations, zero
invalid-sentinel errors, and equal outputs.  The first full-sweep direct-lookup prototype changed
three YFCC =W=2= cells by at most 0.00014 recall; it was therefore rejected on semantics as well as
performance.  A subsequent corrected direct-lookup gate and the final lazy-initialization gate are
bit-for-bit identical to the reference outputs.

The matched 10,000-query GPU policy sweep contributes 120 aggregates: five policies times six
=(L,W)= cells on each of four workloads.  Every aggregate covers exactly 10,000 queries (five
disjoint YFCC shards or one ArXiv shard) and has zero filter violations and zero invalid-sentinel
errors.  Intrinsic underfill is preserved and reported rather than treated as malformed output.

Both CPU runners pass their native self-tests.  The FAISS test proves the degree-derived workspace,
an unaligned 3-by-37 bitmap, and the regression where a passing upper-layer entry point also occurs
in the deterministic ten-ID seed prefix without producing a duplicate result.  The ACORN test
proves metadata-independent topology, entry-point filtering, serialization, and the same unaligned
bitmap.  Its seeded fixtures additionally prove an exact zero-seed reference path, passing-entry
overlap without duplication, a rejected zero-distance entry that evicts a seed from the bounded
candidate heap without losing it from results, fewer-than-ten passing rows, and empty rows.
Across all 347 final CPU aggregate points, every point contains exactly 10,000 queries and
has zero filter violations, zero malformed-sentinel rows, and zero duplicate-output rows.  Every
YFCC aggregate combines exactly five disjoint shards; every ArXiv aggregate contains its one
10,000-query set.  Algorithmic underfill is reported separately: for example ACORN-gamma underfills
130 EMIS queries even though at least ten database rows pass, which is a search-reachability result
rather than a sentinel-format failure.

The NVIDIA L4 has 58 SMs and 23,034 MiB memory.  CUDA function attributes for the reference and
experimental kernels are identical after removing the per-parent counter:

| Threads/CTA | Registers/thread | Dynamic shared memory | Static shared memory | Active CTAs/SM |
|-------------+------------------+-----------------------+----------------------+----------------|
|          64 |               64 |              17,876 B |                  0 B |              5 |
|         128 |               64 |              17,876 B |                  0 B |              5 |
|         256 |               64 |              17,876 B |                  0 B |              4 |

Thus neither rejected optimization changed an occupancy tier.  At =L=128, =W=1=, adaptive tiled
NaviX, 256 threads is 1.7% faster than 128 threads on EM, 1.1% on EMIS, and 3.0% on R despite one
fewer resident CTA.  The existing tiled scheduler is 0.50%, 0.67%, and 1.61% faster than the serial
scheduler on EMIS, EM, and R respectively at 256 threads.

Nsight Compute and Nsight Systems are not installed in this environment.  Consequently this report
does not invent stall-reason or memory-throughput counters; conclusions about the rejected direct
lookup are limited to exact output, CUDA resources, and repeated end-to-end timing.

* Optimization ablations

** Direct bitmap specialization: rejected

The first full-sweep direct-lookup prototype was systematically slower: YFCC -0.482%, EM -0.542%,
EMIS -0.455%, and R -0.602% mean QPS versus reference.  Its minimum/maximum cell deltas on YFCC
were -0.837%/-0.075%.  It also changed aggregate recall by 0.00005--0.00014 in three YFCC =W=2=
cells, so those measurements are retained only as a rejected ablation and excluded from the
primary Pareto figures.

After removing the experimental counter and using a smaller 10,000-query gate, all eight matched
points remained slower:

| Workload | L=128 QPS delta | L=256 QPS delta | Recall delta |
|----------+-----------------+-----------------+--------------|
| YFCC     |         -0.773% |         -0.686% |     0.000000 |
| EM       |         -0.594% |         -0.725% |     0.000000 |
| EMIS     |         -0.512% |         -0.555% |     0.000000 |
| R        |         -0.750% |         -0.765% |     0.000000 |

The generic bitmap device call is already optimized effectively by device LTO.  Hoisting its row
descriptor added a per-query CTA barrier and readback without reducing graph, hash, or distance
traffic, so the specialization fails the acceptance gate.

** Lazy bridge/count initialization: performance-neutral

With the direct descriptor removed, the experimental kernel only skips initialization of bridge
slots outside the compacted prefix and counts overwritten by every parent lane.  Exact output still
passes.  Deltas are -0.096%/+0.218% on
YFCC, -0.078%/-0.010% on EM, -0.022%/-0.115% on EMIS, and -0.071%/+0.049% on R for =L=128/256=.
This is timing noise, far below the 2% retention threshold.  It is not promoted as an optimization.

** Scheduler and distance work

The reference already coalesces one 32-ID graph row per warp, retains grandchildren in registers,
commits bridge rows deterministically, computes distance only for admitted passing nodes (plus
rejected first-hop nodes required for directed ordering), and avoids a =D^2= shared buffer.  The
attempted more aggressive producer/consumer rewrite deadlocked under divergent early exits and was
discarded before measurement.  Preserving the reference synchronization schedule is required for
both correctness and stable performance.

high-recall region, blind two hop is the strongest general policy.  Adaptive Kuzu reduces work and

small recall increment matters.  Adaptive-paper thresholds do not produce a universal advantage.

The same FAISS HNSW graph is used by all three FAISS-NaviX query sets.  ACORN-1 likewise uses one
independent ArXiv ACORN-1 graph.  ACORN-gamma uses different construction parameters and therefore
different graphs for EM, EMIS, and R.  The final YFCC FAISS and ACORN-gamma graphs use the
JAG-aligned values in the provenance table; obsolete exploratory YFCC graphs are not consumed by
the final CSVs.

Both CPU forks accept dense byte masks, so packed-bitmap-to-byte-mask conversion is performed before
the timed search call.  This measures each native CPU search API rather than an adapter conversion.
GPU timing begins with an already resident packed bitmap and includes its strict seed-selection
kernel.  For this reason CPU/GPU overlay figures are descriptive hardware comparisons, not claims
that mask-representation overhead is identical.

The clean YFCC chunk gate measured 1,444.09, 1,496.35, and 1,533.65 QPS for chunks 128, 256, and
512 respectively at =efSearch=100= with eight threads.  Only 512 lies within two percent of the
best, so all final YFCC CPU sweeps use chunks of 512 queries.  Five native calls collectively cover
the same 10,000 queries; aggregate QPS is =10000 / sum(search_seconds)=.

The complete =8/16/32=-thread gate shows that CPU scaling is method dependent.  At
=efSearch=100=, 32 threads is fastest for every YFCC method and every ACORN method; 16 threads is
slightly faster for FAISS-NaviX on each ArXiv workload.  Accordingly, conditional deep search uses
32 threads.  Tables and Pareto curves choose the fastest measured resource setting at each recall
point rather than assuming that 32 threads always wins.

The low ACORN-1 values are not parser errors: predicates are satisfied, sentinels are valid, and
even =efSearch=750= reaches only 0.89392/0.84046/0.86886 recall on EM/EMIS/R and 0.32283 on YFCC.
Giving ACORN-1 NaviX seeds changes those maxima only to 0.89410/0.84350/0.86901 and 0.38798.
Initialization is therefore not its main limitation.  Increasing YFCC FAISS-NaviX from
=efSearch=100= to 750 moves aggregate recall only from 0.77396 to 0.79664; reference ACORN-gamma
moves from 0.58614 to 0.61513 and seeded ACORN-gamma from 0.72524 to 0.76141.  The deep points rule
out an accidentally shallow base sweep.

The comparison also has an important seeding asymmetry.  Bitmap GPU NaviX extracts up to =k=
guaranteed-passing seeds before graph traversal, and FAISS-NaviX deterministically scans the byte
mask for its first ten passing IDs inside the native search call.  Reference ACORN starts from its
ordinary hierarchical entry point and has no global passing-seed prepass or exact fallback.  For
=gamma=1= it blindly examines first- and second-hop neighbors, but only passing nodes persist in
the candidate queue.  A sparse query can therefore drain that queue before it finds ten results.
The 4,422 ACORN-1 and 3,274 ACORN-gamma YFCC underfills persist at =efSearch=750=.  They must not be
attributed solely to two-hop expansion or graph topology, because reference ACORN lacks the global
passing-seed prepass used by both NaviX implementations.  The implemented non-reference ablation
settles that ambiguity: ten deterministic seeds reduce both YFCC underfill counts to zero.
At =efSearch=750=, seeding raises ACORN-gamma from 0.61513 to 0.76141, closing 80.6% of its recall
gap to FAISS-NaviX's 0.79664 on the same masks.  The remaining 0.03523 gap despite matched seeding is
evidence for traversal and/or graph-topology differences.  ACORN-1's much smaller 0.06515 gain
likewise shows that seeds are necessary for sparse-result completeness but not sufficient to make
every ACORN graph/search variant competitive.

* Limitations and conclusion

The GPU optimization result is negative but useful: the current reference kernel is already within
measurement noise of the safe implementation-level improvements tested here.  Bitmap predicate
evaluation and unused bridge initialization are not material bottlenecks.  Larger gains require an
algorithmic reduction in graph/hash/distance work, not a direct rewrite of the packed-bit test.

The algorithmic data also rejects a universal winner.  Strict bitmap seeding plus NaviX solves
EMIS's correlation failure under B0, while the simpler accumulator is substantially faster on EM
and reaches slightly higher recall than NaviX on YFCC.  YFCC remains a reachability problem for the
predicate-only traversal at B0.  The native CPU controls strengthen rather than weaken that
conclusion.  Reference ACORN-gamma's apparent 0.615 YFCC ceiling was substantially a seeding
artifact: matched deterministic seeds raise it to 0.761 and eliminate all underfill.  However,
deeper FAISS-NaviX still reaches 0.797, and neither method reaches 0.90 despite the ACORN graph being
15.42 GB and taking 6.26 hours to construct.  ACORN-1 remains noncompetitive even after matched
seeding.

The GPU policy sweep further shows that the adaptive decision is a throughput optimization, not a
recall requirement.  Forced blind two hop is the strongest general high-recall policy and is much
faster than forced directed expansion at comparable recall.  Adaptive Kuzu improves the
intermediate-recall frontier on EM and R, but policy selection barely changes YFCC's approximately
0.704 ceiling.  YFCC is therefore not failing because the adaptive thresholds choose the wrong
two-hop variant.

Therefore the actionable GPU conclusion is twofold.  First, there is no retained low-level NaviX
kernel optimization from this study: the reference fused kernel is already efficient for the safe
changes tested.  Second, filter-aware traversal is highly valuable on correlated EMIS but neither
adaptive two-hop traversal nor ACORN-style neighborhood enrichment universally solves YFCC's
extremely sparse predicate connectivity.  Deterministic passing seeds are necessary to prevent
sparse-query frontier underfill and explain most of ACORN-gamma's gap, but the residual deep-search
gap proves that seeds alone are insufficient.  Progress on that regime requires a fallback or a
more information-rich data structure, rather than another packed-bit-test micro-optimization.
