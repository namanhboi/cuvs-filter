* Scope and frozen experiment contract

This document is the executable handoff for the experiments used by the RETRIEVE paper.  Run all
commands from the isolated implementation checkout at =/home/ubuntu/cuvs-filter-retrieve= unless a
section explicitly changes directory.  Do not use the development checkout at
=/home/ubuntu/cuvs-filter= to produce paper results.

The production experiment has four inputs:

1. The SINGLE_CTA resident-bitmap GPU graph sweep: CAGRA-Base, CAGRA-Retain, CAGRA-NaviX, and the
   two matched-seed controls.
2. The masked-exact GPU control through the public =cuvs::neighbors::brute_force= API.
3. Native FAISS-NaviX and ACORN CPU context runs.
4. A SHA-256-bound manifest of supporting diagnostics.

The GPU graph configuration is fixed at CAGRA graph degree 32/intermediate degree 64, =k=10=,
=max_queries=512=, squared L2, SINGLE_CTA, and a resident per-query bitmap.  The primary B0 sweep
contains exactly =(L,W)={(64,1),(128,1),(128,2),(256,1),(256,2),(512,2)}= with
=max_iterations=0=.  Correctness uses the first 1,000 queries and one repetition.  Reported
throughput uses all 10,000 queries and three repetitions.

Never overlap the GPU graph suite, masked-exact suite, CPU context suite, graph construction, or
another substantial CPU/GPU job.  Even though the CPU suite does not launch CUDA kernels, its
memory traffic and host scheduling can perturb GPU measurements.  Run one production suite at a
time on an otherwise idle machine.

* GPU graph experiment

** Correctness and complete B0 sweep

Run these stages serially:

#+begin_src sh
cd /home/ubuntu/cuvs-filter-retrieve
export RETRIEVE_DATA_ROOT=/home/ubuntu/cuvs-filter/datasets

benchmarks/retrieve_workshop/gpu_graph/run_gpu_graph.sh analyze
#+end_src

The final =analyze= invocation performs full SHA-256 hashing of resident inputs.  Do not pass
=--skip-full-input-hashes= for paper data.  That option is used internally only for the incremental
deep-run stop test.

Each reported repetition times the complete cuVS-bench search call.  For bitmap-seeded methods
this includes the seed-selection kernel and graph-search kernel.  It excludes index loading, host
configuration parsing, bitmap construction, and installation of the already-resident bitmap.
Consequently these are resident-bitmap query-time results, not predicate-construction results.

YFCC executes as four 2,048-query shards plus one 1,808-query shard.  For each repetition, its
aggregate throughput is exactly =10000 / sum(query_count_of_shard / shard_QPS)=.  Only after this
serial aggregation are the median, minimum, and maximum calculated across three repetitions.

** Optional targeted deep runs

The B0 analyzer writes =${RETRIEVE_RESULT_ROOT}/analysis/deep_candidates.json=.  Review that file
and retain only workload/method pairs for which a deeper diagnostic answers a paper question.
Deep search is not an unconditional Cartesian sweep.

#+begin_src sh
cd /home/ubuntu/cuvs-filter-retrieve
benchmarks/retrieve_workshop/gpu_graph/run_gpu_graph.sh generate \
  --deep-selection "${RETRIEVE_RESULT_ROOT}/analysis/deep_candidates.json"
benchmarks/retrieve_workshop/gpu_graph/run_gpu_graph.sh deep
benchmarks/retrieve_workshop/gpu_graph/run_gpu_graph.sh analyze
#+end_src

For each selected pair, deep search retains only =(64,1)= and =(512,2)= and tries explicit
=max_iterations={522,1044,2088,4176,7569}=.  It analyzes after each depth and stops that pair when
either cell reaches recall 0.90.  To make a deliberately preliminary pass stop at 1044, for
example, set =RETRIEVE_DEEP_MAX_ITERATION=1044=; a later =deep= invocation resumes from complete
depth groups.  Paper analysis marks only points through the first target-reaching depth as
eligible, while retaining every measurement in CSV.

The timed exact search call includes bitmap population counting, query norms, sparse bitmap-to-CSR

=provenance/gpu_memory/=.  Do not use =RETRIEVE_EXACT_AVAILABLE_BYTES= in a paper run; it is only a

=${RETRIEVE_EXACT_RESULT_ROOT}/analysis/exact_summary.csv=.  The adjacent measurement CSVs,

results pass only with =native_l2_cutoff_recall= equal to 1.0, zero native-L2 cutoff errors, and zero

fixed-ID agreement and must remain 1.0 for non-YFCC workloads.  YFCC may report 0.9974 canonical-ID
agreement because its official rank-10 boundary is tied for 55 of the 1,000 correctness queries;
exchanging IDs only at that cutoff is exact under the native-distance gate.

* Failure, overwrite, and resume rules

** General rule

Preserve every failed or partial root.  Do not delete individual raw files, splice measurements
from different roots, or enable overwrite for a paper run.  Diagnose the failure, allocate a new
UTC-tagged root, and rerun the affected production suite from its first stage.  This makes the
binary, library, hardware, data, and repetition identity auditable.

** GPU graph

- =correctness= and =b0= refuse an existing raw JSON unless =RETRIEVE_ALLOW_OVERWRITE=1=.  Do not
  set that variable for production; allocate a new GPU result root after a failure.
- =deep= is the sole resumable exception.  It validates and retains complete earlier depth groups,
  analyzes after each group, and continues at the next missing depth.  Do not edit a completed
  group.
- A changed benchmark binary, =libcuvs.so=, data root, host, or GPU invalidates reuse of the root.

** Masked exact

- Raw output refuses overwrite unless =RETRIEVE_EXACT_OVERWRITE=1=.  Do not set it for production;
  allocate a new exact result root.
- Prepared data may be reused only when its resolved source paths and SHA-256 sidecars match.
  =RETRIEVE_EXACT_FORCE_PREPARE=1= is for an intentional audited replacement, not recovery from a
  benchmark failure.
- A failed memory preflight is a real stop.  Free the GPU or move the entire exact run to a new,
  recorded machine/root; never override available bytes for a paper measurement.

** Native CPU

- The runner creates a run directory atomically, writes =run.failed.json= on failure, and never
  resumes it silently.
- Preserve the failed run, choose a new =RETRIEVE_CPU_RUN_ID=, and restart the complete CPU suite.
  Never merge repetitions or shards across run IDs.

** Corrected YFCC diagnostic

- The legacy diagnostic runner can replace its raw output, so always use a nonexistent
  =YFCC_DIAGNOSTIC_ROOT= and invoke it once.
- A schema mismatch usually means host and device/JIT objects were not rebuilt together.  Rebuild
  the test and both benchmarks, rerun the gate, and use a new diagnostic root.

* Provenance and interpretation checklist

- [ ] Source repos were committed and clean before timed execution.
- [ ] GPU identity is the intended NVIDIA L4; no production suites overlapped.
- [ ] Correctness gates passed before throughput.
- [ ] GPU and exact raw records declare =OutputSetSemanticsVersion=1=.
- [ ] Recall, underfill, and missing-result accounting use distinct valid output IDs.
- [ ] Retain, NaviX, and masked exact have zero duplicate-output queries; native Base duplicates are
  reported rather than credited.
