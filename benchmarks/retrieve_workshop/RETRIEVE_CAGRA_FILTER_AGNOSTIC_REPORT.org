* Frozen research scope

** Research question

The study asks how far traversal-only, predicate-agnostic techniques can improve filtered search
over an unchanged CAGRA graph on a GPU.  The graph is constructed without using a query predicate.
At search time, each query supplies a resident packed bitmap describing the legal base IDs.

The primary comparison separates two failure modes:

1. *Retention loss*: a legal, high-quality node is evaluated but disappears from CAGRA's bounded
   search state before final filtered output.
2. *Exploration loss*: the traversal spends its finite distance budget in non-passing regions or
   cannot continue through a sufficiently useful passing frontier.

CAGRA-Retain targets the first problem without changing traversal.  CAGRA-NaviX targets traversal
by retaining a predicate-clean frontier and adaptively using one- or two-hop expansion.  The
matched-seed controls isolate entry-point availability from the traversal/retention policy.  The
exact bitmap scan gives the non-graph control.

** In scope

- CAGRA graph search with the existing graph fixed at =G=32= and =IG=64=.
- SINGLE_CTA search, squared L2, =k=10=, and =max_queries=512=.
- Resident, per-query, row-major packed bitmaps.
- YFCC-10M and ArXiv EM, EMIS, and R workloads.
- CAGRA-Base, CAGRA-Retain, and CAGRA-NaviX as the primary GPU methods.
- Matched deterministic passing-seed controls as ablations.
- B0 search and narrowly selected deeper-budget diagnostics.
- Exact masked brute-force search as a control.
- Native FAISS-NaviX and ACORN results as qualitative CPU context only.

** Explicitly out of scope

- A new supported cuVS public API or ABI.
- FAVOR scoring, retention penalties, or FAVOR-vs-CAGRA claims.
- MULTI_CTA, MULTI_KERNEL, persistent search, dynamic batching, or refinement.
- Predicate evaluation, UDF execution, or bitmap construction time.
- Filter-aware graph construction or a GPU ACORN/MCI implementation.
- Index-build time, index-update cost, distributed search, or out-of-core execution.
- Absolute CPU/GPU speedup claims.
- Native-uint8 exact-scan throughput for YFCC.

** Frozen hypotheses / evaluation questions

- *RQ1 -- Retention:* Does CAGRA-Retain move the QPS--recall Pareto frontier relative to
  CAGRA-Base while keeping traversal identical?
- *RQ2 -- Traversal:* Does CAGRA-NaviX improve recall within B0 when the passing subgraph is
  reachable and locally useful?
- *RQ3 -- Entry points:* How much of each method's behavior is explained by deterministic access
  to passing seeds rather than its subsequent traversal policy?
- *RQ4 -- Hard predicates:* When a graph method misses the target, is the gap closed by a deeper
  budget, or does it persist despite additional work?
- *RQ5 -- Exact boundary:* What query throughput does exact resident-bitmap search provide under
  the explicit exact-control timing contract?
- *RQ6 -- CPU context:* Do native CPU NaviX/ACORN curves show qualitatively similar or different
  algorithmic behavior, without treating the systems as an apples-to-apples speed comparison?

* Terminology and invariants

| Term | Meaning in this artifact |
|-
| Filter/predicate agnostic | The CAGRA graph topology is built independently of the query bitmap. |
| Resident bitmap | A packed per-query bitmap already installed on the GPU before timed graph search. |
| =L= / =itopk= | Capacity of CAGRA's internal top-k/frontier state. |
| =W= / =search_width= | Number of selected parents expanded per iteration. |
| B0 | =max_iterations=0=, which delegates to CAGRA's automatic budget; it does *not* mean zero iterations. |
| Deep point | An explicit positive =max_iterations= value used only after the B0 gate. |
| Valid GT | In-range ground-truth IDs; out-of-range fixed-width padding is excluded. |
| Passing node | A source ID whose bit is set for the current query. |
| Matched seeds | The same deterministic first-=k= passing bitmap IDs supplied to a CAGRA control. |
| Underfilled query | Fewer than =k= legal output IDs are returned, interpreted together with legal GT cardinality. |
| Pareto point | A measured point not dominated by another point of the same method in both recall and QPS. |

The paper result width and ground-truth width are both exactly =k=10=.  The exact-control
preparation rejects a GT matrix whose width is merely greater than ten.

** Resident bitmap contract

- The input is one packed bitmap row per query and one bit per source-order base ID.
- Graph configs use =filter.kind="bitmap"= and require an identity source-ID index.  This avoids
  silently comparing source-order bitmap/GT IDs with a remapped internal graph space.
- The seed selector contains a correct source-remapping fallback, but the frozen paper
  configurations deliberately reject remapped indices through
  =require_identity_source_indices=true=.
- YFCC is split into five serial query shards to bound resident bitmap memory.  ArXiv uses one
  shard per predicate/phase.
- Query offsets are carried explicitly so that a shard's bitmap rows, query vectors, and GT rows
  remain aligned.

** Bitmap-seeded control

For each search-call shard, =select_navix_bitmap_seeds= launches one warp-sized CTA per query.  On
the identity-ID fast path, lanes load packed 32-bit bitmap words coalescently and lane zero emits
at most =k= set bits in ascending internal-node order.  It stops once =k= passing IDs have been
found; an underfilled row is scanned through its legal graph domain.  The selector records seed
counts and inspected units in preallocated device buffers.

The seed selection kernel executes inside the timed cuVS-bench search call, while its scratch
allocation occurs during setup.  The graph kernel computes distances only for valid supplied
seeds, inserts only those seeds into the visited structure, leaves remaining initial slots
invalid, and returns legal invalid sentinels for an empty row.  It does not add ordinary random
CAGRA starting candidates to fill missing seed slots.

Two uses are frozen:

- CAGRA-NaviX uses strict bitmap seeds for its primary curve.
- =default_cagra_seeded= and =default_cagra_accumulator_seeded= use the same seed selector as an
  entry-point ablation.  These curves must be labeled as controls, not primary methods.

** CAGRA-Base

CAGRA-Base preserves CAGRA's distance-first fused frontier and default filtering behavior.  The
predicate governs legal output, but no dedicated passing-result accumulator is enabled and the
NaviX traversal policy is absent.  It is configured with =filter_mode=default= and
=favor_udf_passing_accumulator=false=.

** CAGRA-Retain

CAGRA-Retain executes the same parent selection, graph expansion, raw-distance computation,
visited checking, and bounded frontier evolution as CAGRA-Base.  Its only algorithmic addition is
a bounded shared-memory top-=k= accumulator for the best passing nodes observed so far.  The final
output is taken from this accumulator.  It is intended to measure retention loss; it must not be
described as changing which graph nodes are explored.

The benchmark-private switch is =favor_udf_passing_accumulator=true=.  The name is historical;
this frozen experiment uses =filter_mode=default= and does not enable FAVOR scoring.

** CAGRA-NaviX

CAGRA-NaviX keeps CAGRA's fused frontier and raw-distance ordering but restricts its persistent
search frontier to passing candidates after strict bitmap seeding.  For each selected parent it
examines first-hop neighbors, measures their local passing yield, and selects one of the frozen
adaptive-Kuzu policies:

- one hop when the degree-32 first hop has at least 13 passing nodes;
- directed capped two hop for intermediate yield;
- blind capped two hop when the first hop has at most 4 passing nodes.

The tiled scheduler writes passing children into CAGRA's existing =W*D= candidate tail.  Rejected
first-hop rows occupy a =W*D= bridge array; resident warps load grandchildren and commit candidates
in stable bridge order.  It does not materialize a =D*D= neighborhood.  The frozen settings are
=navix_mode=adaptive_kuzu=, =navix_scheduler=tiled=, =navix_bitmap_seeds=true=, and
=navix_kernel_variant=reference=.

** Exact resident-bitmap control

The exact pipeline uses the existing =cuvs::neighbors::brute_force= interface through a
benchmark-private bitmap wrapper.  It operates on the same source-order bitmaps and GT as the
graph experiment and returns exact squared-L2 top-=k= among passing IDs.

At the current 10% selectivity boundary, cuVS chooses either:

- a sparse path: bitmap population count, bitmap-to-CSR, CSR-to-COO, masked sparse distance, and
  top-k; or
- a dense path: tiled masked distance plus tiled/final top-k.

YFCC uint8 base/query matrices are converted exactly coordinate-by-coordinate to float32 because
the public brute-force instantiations used here are float/half.  The conversion preserves IDs and
coordinate values, but the resulting exact throughput is a float32 control with four times the
native uint8 vector traffic.  ArXiv remains native float32.

The exact-control timed call includes bitmap counting, query norms, optional CSR/COO construction,
distance evaluation, distance/top-k epilogues, and temporary device allocation/deallocation.  It
excludes bitmap materialization/upload, predicate evaluation, and uint8 conversion.

** Native CPU context

The CPU pipeline runs already-built FAISS-NaviX, reference ACORN-1, and reference ACORN-gamma
adapters and graphs.  Optional ACORN variants with NaviX seeds remain in tables but not the main
CPU Pareto plot.  CPU adapters unpack the packed bitmap to their dense byte-mask API outside the
timed search call.  Different graph families, graph parameters, thread counts, and timing
boundaries make these qualitative context curves, not GPU speedup baselines.

** Optional deep protocol

Deep runs are diagnostic extensions, not an unconditional Cartesian sweep.  Run only
workload/method pairs whose best six-cell B0 recall is below 0.90, after manually reviewing
=analysis/deep_candidates.json=.  Retain only =(L,W)=(64,1)= and =(512,2)= and test explicit
=max_iterations={522,1044,2088,4176,7569}= in increasing order.  Stop a series after either cell
first reaches 0.90 recall.  Raw CSV retains later measured points if they exist, but paper plots
exclude over-search points after the first target-reaching depth.

** GPU graph timing and aggregation

Each repetition times the complete cuVS-bench search call.  Seeded methods include the bitmap
seed-selection kernel and graph-search kernel in that call.  The timing excludes graph/index load,
host configuration parsing, and construction or host-to-device installation of the resident
bitmap.

YFCC's five shards execute as serial host calls.  For each =repetition_index= independently:

#+begin_example
seconds_rep = sum(query_count_shard / QPS_shard)
QPS_rep     = 10000 / seconds_rep
#+end_example

Only then are median/min/max computed over the three repetitions.  Never average shard QPS and
never combine different repetition indices.

** GPU graph correctness gate

The analyzer must observe all expected methods, B0 cells, shards, and repetitions and no extra
ones.  For every raw record it requires:

- =algo="single_cta"=, =filter_mode="default"=, =k=10=, and =max_queries=512=;
- method label and runtime flags matching the generated manifest;
- =require_identity_source_indices=1=;
- zero =FilterViolations=;
- zero =InvalidSentinelErrors=;
- zero =DuplicateOutputQueries= for Retain and NaviX.  Native fused Base and its matched-seed
  control may report repeated valid IDs when filtered output is underfilled; those rates remain in
  every raw/summary artifact and are not treated as successful extra neighbors;
- finite positive QPS, Recall@10 in =[0,1]=, and a valid-GT fraction in =(0,1]=.

Underfilled-query and missing-slot counters count distinct valid output IDs, so a repeated Base ID
is treated as a missing unique result rather than a filled slot.  Missing mandatory correctness
counters or =OutputSetSemanticsVersion=1= fail analysis rather than being treated as current data.

Both =Recall= and =ValidGTRecall= are set-valued in the frozen benchmark binary: a repeated output
ID receives at most one match credit.  This prevents native Base duplicates from inflating quality
while leaving the search output and its duplicate-rate diagnostic unchanged.  The analyzer rejects
duplicates from either new method because their accumulator/frontier implementations are designed
to emit unique results.

* Frozen exact-control protocol

** Preparation and cache validation

=prepare_exact_workload.py= binds a prepared manifest to both the resolved source-base path/full
SHA-256 and the resolved source-bitmap-manifest path/full SHA-256.  A same-shaped input is not a
valid cache key.  YFCC float conversions also have sidecars binding complete source and target
path/size/SHA-256 records.  Missing, legacy, or stale provenance fails preparation.

Use =RETRIEVE_EXACT_FORCE_PREPARE=1= only to explicitly replace stale/legacy preparation state.
It is not a substitute for recording which inputs changed.

Preparation additionally enforces:

- base/query dimension agreement;
- contiguous query-shard coverage;
- exact ground-truth width =k=10=;
- legal bitmap shape and zero unused tail bits;
- exact per-shard bitmap population counts;
- a valid conservative GPU-memory estimate for every shard.

The five-test exact pipeline verifies the cache contract rather than only its happy path.  It
accepts byte-identical reuse, rejects a same-shaped source whose contents changed, rejects a
changed source bitmap manifest, permits explicit refresh with =--force=, validates conversion
sidecars, rejects GT width 11 when =k=10=, and checks the memory gate at exactly the required byte
count and at one byte below it.  The prepared production snapshot is rooted at
=/home/ubuntu/retrieve_workshop_data/exact_bitmap/= and contains all eight manifests listed in the
static validation snapshot above.

** GPU memory preflight

The estimate includes resident float32 base vectors, base norms, float32 queries, bitmap, output
IDs/distances, timed query norms, and path-specific workspace:

- sparse: float CSR values, int64 CSR columns/row offsets, and int64 COO rows;
- dense: the modeled dense distance tile and tiled top-k intermediates.

The required free memory is:

#+begin_example
required = modeled_peak + max(2 GiB, 0.20 * modeled_peak)
#+end_example

The margin covers CUDA/RMM workspaces, select-k/conversion workspace, fragmentation, and
unmodeled context overhead.  Before each production shard, =gpu_memory_preflight.py= queries the
first CUDA-visible GPU, writes a PASS/FAIL record under =provenance/gpu_memory/=, and refuses to
launch if free memory is below the recorded requirement.  =RETRIEVE_EXACT_AVAILABLE_BYTES= is a
test/debug override and must not be set for a paper run.

This is a conservative launch gate, not a measured peak-memory result.

** Exact correctness gate

For each workload, the exact analyzer requires:

- valid-GT recall exactly 1.0;
- zero predicate violations;
- zero invalid-sentinel errors;
- zero duplicate-output queries;
- observed underfill and missing slots exactly matching legal GT cardinality;
- the complete configured shard/repetition sets;
- a matching PASS memory-preflight record for every production shard.

ArXiv fixed-width GT may contain out-of-range padding for an intrinsically underfilled query.
Those values are excluded from the denominator; they are not accepted as neighbors.

** GPU graph gates

- =provenance/run.json= records git HEAD/status, host, GPU, CPU, relevant environment, resolved

  =OutputSetSemanticsVersion=1=.  This prevents an older result root from being relabeled by a
  newer analyzer.
- Reusing a result root is rejected if binary/library hashes, data root, host, or GPU change.
- Generated manifests freeze exact methods, search points, shard coverage, query count, and
  repetitions.
- Raw JSON cannot be overwritten without explicit =RETRIEVE_ALLOW_OVERWRITE=1=.
- Analysis rejects missing/extra shards, points, or repetitions and checks method labels/runtime
  flags against each manifest.
- Final analysis records SHA-256 for configs, source bitmap manifests, raw results, and all resident
  base/query/GT/bitmap/index inputs.
- A final paper artifact with =resident_input_hash_status= saying hashes were skipped is invalid.

** Exact-control gates

- Prepared cache reuse requires source base and source bitmap manifest full SHA-256/path matches.
- UInt8 conversion reuse requires verified source and target sidecars, not shape alone.
- GT width must be exactly ten and bitmap populations are counted during preparation.
- Every config copies the corresponding per-shard memory requirement.
- Every process requires a matching preflight PASS record with available memory at least required
  memory.
- Raw JSON cannot be overwritten without explicit =RETRIEVE_EXACT_OVERWRITE=1=.
- Production analysis requires run provenance, complete phases, all correctness conditions, and
  the complete shard/repetition sets.
- =analysis/final_hash_manifest.json= binds configs, raw results, source/prepared manifests,

* Limitations and threats to validity

- *Graph scope:* one CAGRA topology (=G=32=, =IG=64=) is tested.  Results do not establish behavior
  for other degrees, construction algorithms, or filter-aware graphs.
- *Kernel scope:* only SINGLE_CTA is frozen.  Batch-one MULTI_CTA latency and MULTI_KERNEL behavior
  are outside this study.
- *Predicate representation:* graph-search timing assumes a resident bitmap.  Predicate/UDF
  evaluation, bitmap creation, transfer, caching, and invalidation costs are excluded.
- *ID scope:* paper configs require identity source indices.  The results do not validate
  performance on compacted/remapped indices.
- *Metric/type scope:* squared L2 and =k=10= only.  YFCC graph search is uint8, while its exact
  control is float32-converted.
- *Budget scope:* B0 plus five explicit deep caps is not proof over all possible traversal depths.
- *Accumulator scope:* Retain is bounded to top-=k= passing results and shares the production
  traversal; other accumulator capacities/designs are not evaluated.
- *NaviX scope:* the primary curve freezes adaptive-Kuzu plus the tiled scheduler.  Other NaviX
  policies are not part of the primary matrix.
- *Sharding:* YFCC uses five serial calls.  QPS is corrected by total elapsed search time, but launch
  structure still differs from single-call ArXiv.
- *Exact memory:* the preflight estimate is conservative and not a measured allocator peak.
- *Exact YFCC arithmetic:* byte coordinates convert exactly to float, but large expanded-L2
  intermediates can exceed float's exact-integer range; correctness must be established against GT.
- *CPU context:* CPU and GPU use different graph families, construction parameters, resource
  counts, adapters, and timing regions.
- *Dataset coverage:* two dataset families and four predicate workloads cannot establish universal
  behavior across all correlations/selectivities.
- *Preliminary contribution:* failure modes and promising design directions may be stronger than a
  complete general solution; claims should match the workshop's preliminary-results scope.
