#+title: RETRIEVE exact bitmap control

* Purpose

This benchmark measures exact, per-query bitmap-filtered squared-L2 search using the existing
=cuvs::neighbors::brute_force= API.  It is an exact-scan control for the YFCC-10M and ArXiv EM,
EMIS, and R graph-search experiments; it does not add or change a public cuVS API.

The benchmark-private brute-force wrapper recognizes the same =filter.kind=bitmap= configuration
used by CAGRA.  Each timed =brute_force::search= call includes bitmap population counting, query
norm computation, optional bitmap-to-CSR and CSR-to-COO construction for sparse masks,
masked-sparse or tiled-dense distance evaluation, the distance/top-k epilogues,
invalid-sentinel normalization over the q-by-k output, and temporary device
allocation/deallocation.  Bitmap materialization, host-to-device bitmap upload, and vector/index
preparation occur before timing.

Every generated =exact_summary.csv= row records
=timed_invalid_sentinel_normalization=True=.  Paper staging requires this flag, so a run that
omitted the benchmark-private q-by-k normalization cannot be mistaken for the timed exact control.
Prepared workload manifests carry the same Boolean marker and exact timing-contract text.  Cache
reuse, config generation, and analysis all reject a legacy manifest that lacks either binding.

YFCC is stored as =uint8=, while public cuVS brute force is instantiated for =float=/=half=.  The
preparation step converts both its base and every query shard to =float32=.  Every byte coordinate
is represented exactly, and source IDs, bitmaps, and ground truth are unchanged.  This is still a
float32 =L2Expanded= control rather than a native-uint8 throughput baseline: norm/dot
intermediates can exceed =2^24=, so distance ties/order are validated empirically against the
original ground truth, and vector traffic is four times the native uint8 footprint.  The
post-timing validator recomputes squared L2 with wide accumulation from the prepared coordinates;
because the converted coordinates are exact byte values, this recovers the native-uint8 squared-
L2 ordering without adding work to the reported QPS interval.  ArXiv uses its native float32
files.

* Commands

One-command deterministic smoke test.  It runs separate sparse/CSR and dense/tiled fixtures; both
include underfilled rows and the dense fixture also includes an empty predicate row:

#+begin_src sh
benchmarks/retrieve_workshop/exact_bitmap/run_exact.sh smoke
#+end_src

Full experiment:

#+begin_src sh
benchmarks/retrieve_workshop/exact_bitmap/run_exact.sh all
#+end_src

Individual stages are =build=, =prepare=, =configs=, =correctness=, =throughput=, and =analyze=.
Override locations with =RETRIEVE_DATA_ROOT=, =RETRIEVE_BITMAP_ROOT=,
=RETRIEVE_EXACT_DATA_ROOT=, =RETRIEVE_EXACT_RESULT_ROOT=, =RETRIEVE_EXACT_BENCH_BIN=, and
=RETRIEVE_EXACT_LIBCUVS=.  Existing NaviX bitmap manifests are the predicate source.  YFCC keeps
its 2,048/2,048/2,048/2,048/1,808-query shards; each ArXiv predicate uses one 10,000-query bitmap.

Prepared manifests are reusable only when the resolved source-base path and full SHA-256 plus the
resolved source-bitmap-manifest path and full SHA-256 still match.  UInt8-to-float conversions have
their own source/target SHA-256 sidecars; a same-shaped stale conversion is not accepted.  Use
=RETRIEVE_EXACT_FORCE_PREPARE=1= to replace stale or legacy preparation state explicitly.

Preparation records an exact bitmap population and a conservative GPU-memory estimate for every
shard.  The estimate models the resident float base, norms, queries, bitmap and outputs; the sparse
CSR/value/index and COO-row allocations or dense tiled workspace; and adds
=max(2 GiB, 20% of modeled allocations)= for CUDA/RMM workspaces and fragmentation.  Before every
benchmark process, the runner compares this requirement with free memory on the first
CUDA-visible GPU, writes the decision under =provenance/gpu_memory/=, and refuses to launch on
failure.  =RETRIEVE_EXACT_AVAILABLE_BYTES= is a test/debug override, not a paper-run setting.

Correctness runs use the fixed first 1,000 queries and one repetition.  Reported throughput runs
use all 10,000 queries and three repetitions.  YFCC aggregate QPS is exactly
=10000 / sum(shard search seconds)=, never an arithmetic mean of shard QPS.

* Outputs and correctness contract

Generated files live under =results/= by default:

- =raw/<phase>/<workload>/shard_NN.json=: unmodified Google Benchmark JSON.
- =provenance/gpu_memory/<phase>/<workload>/shard_NN.json=: mandatory pre-launch free-memory
  decision and the complete estimate used for it.
- =analysis/exact_shard_measurements.csv=: each shard/repetition, including QPS and all checks.
- =analysis/exact_aggregate_measurements.csv=: each workload/repetition after serial shard
  aggregation.
- =analysis/exact_summary.csv=: median, minimum, and maximum QPS plus exact recall.
- =analysis/exact_results.json=: machine-readable timing contract, correctness rules, and summaries.

The analyzer reports =valid_gt_recall= as canonical fixed-ID agreement over legal ground-truth IDs
using distinct output-ID set semantics: a repeated output ID can receive match credit at most once.
Raw records must declare =OutputSetSemanticsVersion=1= and run provenance must bind the
=distinct_valid_output_ids_v1= contract, so legacy slot-counted results cannot be staged.  This
fixed-ID metric is not by itself a valid exactness gate because the legal rank-=k= boundary can be
tied in any workload.  For example, YFCC reports 0.9974 canonical-ID agreement on the 1,000-query
correctness set and 0.99726 over the full 10,000-query set; 55 correctness queries have a
non-unique legal tenth-distance cutoff.  ArXiv-R likewise reports 0.99999 canonical agreement over
100,000 output slots because one returned ID differs at a legal cutoff tie.  These values remain
useful diagnostics, but no workload is required to reproduce one arbitrary canonical choice among
equal-distance IDs.

The tie-aware exactness gate instead requires =native_l2_cutoff_recall= equal to 1.0,
=native_l2_cutoff_errors= equal to zero, and =native_l2_strict_prefix_errors= equal to zero.  Thus every unique legal
output is within the official native squared-L2 rank-=k= cutoff, and every official GT ID strictly
closer than that cutoff is retained; only IDs tied at the cutoff may be exchanged.  The native-L2
validator runs after the timed search and is excluded from QPS.  Predicate violations,
invalid-sentinel ID/distance/ordering errors, and duplicate-output queries must also be zero, and
observed underfilled/missing output slots must exactly match legal GT cardinality.  ArXiv-EM has
one intrinsically underfilled query whose fixed-width GT row contains out-of-range padding IDs;
those IDs are not neighbors and are excluded from all exact denominators.  The analyzer also
requires the exact configured shard/repetition sets and a passing memory-preflight record for every
production shard, and exits nonzero on any violation.

Consequently, the native-L2 cutoff and strict-prefix conditions above are the authoritative
exactness gate for every workload.  Canonical =valid_gt_recall= is always reported, but it is never
used as a pass/fail threshold.
